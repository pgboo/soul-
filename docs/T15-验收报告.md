## 四、测试脚本修正记录（非源码缺陷）

初次运行有 5 项「失败」，定位如下，**均非被测源码 BUG**：

1. **A2 / A2b（断言错误）**：脚本误把成功码写成 `code==0`，实际统一返回体成功码为 **`200`**（见 `ResultCode.SUCCESS(200,...)`）。修正断言后通过。
2. **A3（验证码发送限流串扰）**：`/api/mini/auth/code` 有 60s 发送间隔限制（`SMS_CODE_SEND_INTERVAL_SECONDS=60`），连续两次登录同一手机号时第二次发码被限流 → 登录返回 1002（验证码已过期）。改用**隔离复验脚本 `t15_a3_verify.py`**（每步间隔 62s）后 A3 通过：封禁中 `1003`、解封后 `200`，DB status `2→1`。
3. **B10（验证逻辑错误）**：广场列表按设计**排除本人动态**，脚本原先用发布者视角看不到自己发的动态。改为**他人视角**验证可见性后通过。
4. **B11（路径错误）**：脚本误用 `/api/mini/soul/test/submit`，实际为 **`/api/mini/soulTest/submit`**（见 `SoulTestController` 类注释 `@RequestMapping("/api/mini/soulTest")`）。修正路径后通过。

## 五、遗留观察

1. **【已修复】BUG-6：敏感词重复保存 / 逻辑删除后无法重新添加（撞唯一键返回 500）**
   - **缺陷现象**：对已存在（含已逻辑删除）的 `word` 再次 `save`，返回 `code=500 系统异常`，而非友好业务提示。
   - **真实根因**：
     - `sensitive_word` 表有 `UNIQUE KEY uk_word(word)`，而**逻辑删除不释放唯一键**（行仍在，仅 `is_delete=1`）；
     - MyBatis-Plus 的 `@TableLogic` 会给 `selectCount` 自动追加 `AND is_delete=0`，导致应用层重名校验**看不见已删除的旧行** → 校验放行 → `insert` 撞 `uk_word` → 兜底为 `code=500`。
   - **修复方案（4 处）**：
     1. `sql/schema.sql`：去掉 `UNIQUE KEY uk_word`，改为普通索引 `KEY idx_word`
     2. `SensitiveWordMapper`：新增 `countByWordIncludeDeleted(word, excludeId)`（原生 `@Select`，**绕过 @TableLogic**）
     3. `AdminSensitiveWordServiceImpl.save`：两处重名校验改用它
     4. 线上库：`ALTER TABLE sensitive_word DROP INDEX uk_word, ADD INDEX idx_word(word)`
   - **（复验）新 jar 回归证据**（`backend/target/t15_regress2.txt` / `bug6_check.out`）：
     ```
     首次 save  : code=200 保存成功
     重复 save  : code=400 「敏感词已存在」       (修复前 500)
     delete     : code=200，is_delete → 1
     删除后重加 : code=400 「敏感词已存在」       (修复前 500)
     ```
     **500 崩溃已消除，行为一致、可控。**
2. **广场本人动态不可见**：`DynamicServiceImpl.list` 强过滤 `userId != currentUser`，用户发布后需通过个人主页/详情查看自己的动态。若产品期望广场也展示本人动态，需产品与架构确认。当前按「广场=他人内容」语义，判定为符合设计。
